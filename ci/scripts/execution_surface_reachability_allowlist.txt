# Execution-surface reachability allowlist (check_execution_surface_reachability.py)
#
# Format: one row per line, `<exact tuple text><TAB><reason>` (a literal TAB
# character, never ` | ` — several tuples below pipe their own output
# through `tee`, e.g. `... 2>&1 | tee "$L1"`, so a `|`-based delimiter would
# collide with the tuple's OWN text). `#`-prefixed and blank lines are
# ignored. A row's tuple text is re-verified against the CURRENT registry
# (ci/scripts/**) on every run — a row naming a tuple whose script was
# renamed/deleted, or whose exact command line changed, FAILS as rot; a row
# whose tuple has become reachable on the merge path FAILS as a dead waiver.
# Neither is ever silently skipped.
#
# Every reason below cites STABLE CONTENT (a quoted phrase, a script/job
# name, an invariant this repo's own comments already state), never a bare
# line number — a line number rots the moment ANY unrelated PR touches the
# cited file, including this gate's own introduction (its first version
# cited `ci.yml:1004`, which its own +24-line insertion into ci.yml moved
# to line 1028 in the SAME commit).
#
# HONEST RESIDUAL (see the gate's own module doc "Honest residual" section):
# every row below needs a real CUDA/CUTLASS toolchain to run meaningfully.
# `runpod_gpu_prove.sh` (the driver script several rows below reference) is
# invoked from TWO places, not one: directly by `gpu-prove.yml`
# (`workflow_dispatch` / `pull_request: types: [labeled]` / nightly
# `schedule`), and by the reusable `_gpu-prove-gate.yml` (a release gate
# `uses:`-called from `_pypi-server.yml` — itself called by BOTH
# `pypi-server.yml` (`with: run_gpu_prove: false` — never triggers this
# gate) and `pypi-server-cuda.yml` (`with: run_gpu_prove: true`) — and from
# `server-image.yml` and `release-binaries.yml`).
# NEITHER chain is merge-path: `gpu-prove.yml`'s own triggers are label/
# dispatch/schedule-only; the three `_gpu-prove-gate.yml` callers are each
# scoped to `push: tags: [...]` and/or `workflow_dispatch` (release lanes),
# and where any of them ALSO carries a `pull_request` trigger
# (`pypi-server-cuda.yml`, `server-image.yml`), that trigger's own `paths:`
# filter is scoped to packaging/Dockerfile changes, never `ci/scripts/**`.
# The residual survives via tag/dispatch-gating and path-filter narrowness,
# not via "only one caller" — promoting ANY of these chains to a REQUIRED
# merge-path check is a GitHub branch-protection ruleset setting, not
# committed workflow YAML, so nothing in this checkout can verify it —
# `GPU_PROVE_PROMOTED_TO_REQUIRED` in the gate script stays `False` until a
# human flips it (with a comment recording how the promotion was verified).
# Until then every row below is the honest, written, non-silent choice: each
# tuple stays off the merge path BY NAME, not by omission.

# --- ci/scripts/pod_seed_target.sh's own T1/T1b/T2/T3 (esc-050/esc-051) ---
# The pod auto-seed's own canonical CUDA/CUTLASS-toolchain-gated legs. Each
# reds the WHOLE seed on a fresh pod the moment it regresses (pod_seed_target.sh's
# own module doc). No hermetic ubuntu-latest runner carries `dep:bindgen_cuda`
# / a vendored CUTLASS checkout, so none of these can run on ci.yml's bare
# runners; runpod_gpu_prove.sh carries a byte-identical (or live-run) twin of
# most of them (see the HONEST RESIDUAL note above for that script's own
# two-caller chain), but neither chain is merge-path.
cargo build --release -p jammi-bench --features cuda	T1 (pod_seed_target.sh) — needs the CUDA toolchain (dep:bindgen_cuda); ci.yml's hermetic runners have none. runpod_gpu_prove.sh does not carry this exact `--release` build (only its live it-suite invocations, rows below).
cargo build --release -p jammi-bench --features cuda,jammi-kernels/flash-attn	T1b (pod_seed_target.sh, main-only) — needs a provisioned CUTLASS submodule + nvcc; no hermetic runner has either.
cargo test -p jammi-server --features cuda,live-gpu-tests --test it --no-run	T2 (pod_seed_target.sh) — compile-checks jammi-server's cuda,live-gpu-tests test binary. ci.yml's "Compile-check (gated lanes)" job compile-checks jammi-ai's gpu_capability suite but never jammi-server's `it` suite with the cuda feature; genuinely off the merge path today, not merely mis-normalized.
cargo test -p jammi-ai --features cuda,live-gpu-tests --test gpu_capability --no-run	T2 (pod_seed_target.sh) — the SAME suite ci.yml's "Compile-check GPU-capability suite" step compile-checks, but WITHOUT `cuda` (that step's own comment: "Compile-checked without `cuda`... this stays a CPU-runner step"). The cuda-enabled compile-check has no merge-path twin.
cargo test -p jammi-kernels --features cuda --no-run	T2 (pod_seed_target.sh) — compile-checks jammi-kernels' `cuda_parity` test target (`required-features = ["cuda"]`), the one target ci.yml's own module doc names as uncoverable on the hermetic runner ("CANNOT be covered here... linted instead in runpod_gpu_prove.sh").
cargo clippy -p jammi-kernels --all-targets --features cuda -- -D warnings	T3 (pod_seed_target.sh) — the exact esc-051 tuple. runpod_gpu_prove.sh carries a byte-identical twin, but see the HONEST RESIDUAL note above: neither of that script's two invocation chains is merge-path — green "wiring", dead on the path that gates merges.
