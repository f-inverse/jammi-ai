# Brief DELTA — incremental embedding: versioned result tables over immutable segments with content-hash deltas

Unit: feature, engine core (jammi-db store/index/catalog + jammi-ai pipeline). Independent of PR-C for the store/index mechanism; the sharded (N-worker) path composes with GRAPH and the `embedding` job kind — design for it, do not depend on it.

## The defect, verified on main
A source edit costs a full re-embed. `EmbeddingPipeline::run` scans the whole source and infers every row (crates/jammi-ai/src/pipeline/embedding.rs:15-47,136-151). "Incremental recompute" is table-granular: freshness compares anchors and definition hash (crates/jammi-db/src/store/freshness.rs:1-40) and `recompute` replays the whole producer with `CachePolicy::Bypass` (crates/jammi-ai/src/pipeline/recompute.rs:1-27). Sources are anchored `UnpinnedAtInstant` (embedding.rs:38-47; manifest.rs:836-862); `MutableVersion`/`SourceVersion` anchors are "structurally unreachable" (freshness.rs:36-40). No per-row content hash exists in the embedding output (result_sink.rs:90-93 schema `_row_id,_source_id,_model_id,vector`). The ANN index IS segmented and append-only (crates/jammi-db/src/index/segment.rs:1-30; `append_segment` store/mod.rs:1698-1730, called by embedding.rs:255) — but the merge dedups by row id keeping the NEAREST occurrence (segment.rs:176-213), so an updated row present in two segments is ambiguous, and no tombstone/mask exists (grep: none).

## Design position (validate; refute with a principle or a feasibility fact)
- Versioned result tables over immutable segments, modelled on Lance/Iceberg snapshots (validate against their docs and cite: a version = a manifest listing the live segments + a deletion set; segments are never rewritten; compaction produces a new version). A refresh produces a NEW VERSION of the same logical table: prior segments retained by reference, one new segment for new/changed rows, a deletion set (tombstones by `_row_id`) masking superseded and deleted keys. `search` reads the current version: segment fan-out + mask; the dedup rule becomes "masked rows never appear" (fixes the nearest-wins ambiguity at the root).
- Change detection has two tiers. Tier 1 (ships first, works for EVERY source): per-row content hash of the embedded columns stored in the result table (`_content_hash`); refresh scans the source (O(n) scan, cheap), compares keys+hashes against the current version (O(n) hash join), and infers only the delta (the expensive part). Tier 2 (later, per source kind): a source that exposes a version/changed-since surface prunes the scan. Tier 2 for mutable tables: a TABLE-LEVEL monotonic version is a freshness surface the manifest already anticipates (`MutableVersion`) and is allowed; ROW-LEVEL change tracking on mutable tables is a transition log and violates the leak-guard ("no built-in transition log, no automatic versioning") — deferred, and Tier 1 covers it generically. State this line explicitly.
- Identity (K7): a version's identity folds the parent version + the delta descriptor; a full `recompute` of a versioned table yields a compacted single-segment version and is VALUE-equivalent, not byte-identical, to the chain (state the K4 scope precisely: embedded vs remote must still be byte-identical for the same operation; delta-vs-full is a different operation).
- K1: a new `ProducingDescriptor` arm (or a versioned variant) must have its `replay_descriptor` arm; define replay of a versioned table (replay = full recompute of the CURRENT source state → a new compacted version).
- Actuator, not control loop: `refresh(table)` (name it against existing verb vocabulary) is the actuator; when to call it is the consumer's. `staleness` extends to report "delta available" once Tier 2 exists.
- Compaction is an explicit verb (mechanism); no background compactor (control loop).
- Deletes: a key absent from the source is tombstoned on refresh (default) — decide whether deletes are opt-in (a source that is a rolling window would otherwise erase history) and justify.
- Sharding: a refresh's delta is partitionable by key range into N `embedding` jobs each writing one segment, with a fan-in publishing the version manifest — design the manifest publish as the CAS point so a partial fan-out never publishes; cite GRAPH for the edges but keep this PR independent (single-process refresh ships here).
- Read path: the segment mask must not regress `search_final` rescoring (segment.rs ~:25-40) or exact fallback (`resolve_search_mode`); state the cost of mask application per query.

## Forks
F1. Where the deletion set lives: a per-version Parquet sidecar (Iceberg "delete file" shape) vs. catalog rows. Recommend sidecar (object-store native, one artifact per version, byte-addressable identity) — decide.
F2. Version naming: the `result_tables` row is today the identity (table_name PK). A versioned table needs `table_name` = logical name + a `version` column, or a `result_table_versions` table. K5 append-only migration; SQLite+Postgres parity; the `BuildingTable` lease/CAS funnel must publish a version the same way it promotes a table today.
F3. `_content_hash` algorithm and what it covers (the embedded columns only, in column order, with a type-stable encoding) — K7 completeness: the hash must fold the model_id/task implicitly via the table identity, not per row.
F4. Whether the embedding job kind on wt-C (`ComputeSpec::Embedding`) becomes "embed this key range into a segment" or a new kind — recommend the former with a partition spec; state the wire change only as a follow-up, not this PR.
References to validate: Lance table format (versions/fragments/deletion files), Apache Iceberg spec (snapshots, delete files, compaction), and one vector-DB precedent for tombstoned deletes on immutable segments (e.g. Milvus/Qdrant/Weaviate segment deletes). Cite what each established.

## Acceptance
- Edit one row of a 10k-row source and refresh: exactly 1 row inferred (counted), a new segment with 1 row, a deletion set with 1 key; `search` returns the new vector for that key and never the old.
- Delete one key and refresh: tombstoned; absent from search; present in no segment scan result.
- Full recompute of the versioned table: single segment, value-equivalent results (same top-k ids for a fixed query set), identity distinct from the chain.
- K4: embedded and remote `refresh` produce byte-identical version manifests for the same edit.
- No regression: a never-refreshed table behaves byte-identically to today (goldens/cookbook re-emit).
