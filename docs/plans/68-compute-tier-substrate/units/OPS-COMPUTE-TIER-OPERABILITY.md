## 1. Decisions

| # | Decision | Principle | Code fact |
|---|---|---|---|
| D1 | **Two shutdown modes with PostgreSQL's mapping (R1): SIGTERM = DRAIN (smart), SIGINT = RELEASE (fast); any signal received while draining = RELEASE.** No engine-side drain timeout. | "Engine ships the actuator, never the control loop that pulls it" (`main crates/jammi-ai/src/pipeline/recompute.rs:29-35`); the runtime owns the bound (`terminationGracePeriodSeconds`, `stop_grace_period`). | The engine cannot abort a `spawn_blocking` thread (`crates/jammi-ai/src/fine_tune/worker.rs:1517-1522` runs the trainer on the blocking pool; `:1586-1592` documents that aborting the loop task only cancels at the next `.await`); a tokio runtime drop waits for blocking work (R3), so an in-engine timeout could only duplicate SIGKILL. Orchestrators send one stop signal then SIGKILL (R4, R5) — a second SIGTERM never arrives from Kubernetes, so RELEASE must be reachable by a distinct signal and by an actuator (D13). |
| D2 | **DRAIN keeps the keeper alive, never flips `cancel`, finishes the in-flight job, then closes the session.** | Brief D1: a rollout must not lose in-flight training. | Today's chain is the inverse: serve returns → `_worker` dropped (`crates/jammi-server/src/runtime.rs:1065-1066`, field `:991`) → `EmbeddedWorker::drop` aborts the loop (`worker.rs:1717-1724`) → `session.close()` (`runtime.rs:566`) → keeper `ExitGuard` flips every hold's `lost` (`crates/jammi-db/src/catalog/lease_keeper.rs:188-200`) → trainer skips the bundle (`crates/jammi-ai/src/fine_tune/trainer.rs:1356-1363`) and bails (`:1093-1097`). |
| D3 | **Worker guard hoisted to `BoundServer`** (`BoundChain::take_worker()` called by `OssServer::bind`); chain-level serve paths keep Drop-abort semantics; downstreams take the guard via `ChainParts.worker` or `take_worker`. | Ownership decides who can drain (B4: server and library reach the same primitive). | `BoundChain` privately owns `_worker` (`runtime.rs:991`) and drops it after its own serve (`:1065-1066`); `stop_and_join` takes the `JoinHandle` (`worker.rs:1686-1691`) and `Drop` aborts only inside `if let Some` (`:1718-1724`) — the "no abort after a graceful join" half already exists; the defect is ownership only. `ChainParts.worker` (`:700`) is the precedent for handing the guard out. |
| D4 | **Loop termination is observed through `watch<LoopState>` set by a Drop guard inside the task** (`LoopState { Running, Stopped, Aborted, Failed }`); `release_and_stop` awaits the watch; the `JoinHandle` is awaited only after the watch has reported terminal, and only on the cooperative arm (the abort owner is stated once in §3.1). | A writer placed after `run_until().await` never runs on abort/panic; a Drop guard runs on every exit path. | `ExitGuard` pattern `lease_keeper.rs:183-200`. `stop_and_join` consumes the handle (`worker.rs:1686-1691`), so a second observer cannot join it. |
| D5 | **The worker's `stop` is a `watch<bool>` in `WorkerShared`, not an `AtomicBool` and not a `Notify`**: the loop's idle sleep becomes `select!{ sleep(idle_poll), stop_rx.wait_for(|v| *v) }` and the pre-claim check reads the watch. | D6 | **RELEASE is one mechanism, `release_and_stop`, stated once in §3.4**: phase flip → keeper releases registered holds → sweep #1 → `stop` → cooperative-or-abort keyed on `in_flight` → observe the watch → sweep #2 unconditionally → `delete_worker`. Sweep #2 runs BEFORE `delete_worker` (load-bearing). | Zombie gate must flip before the hold disappears; no abort while a claim transaction can be in flight; the `workers` row outlives the last lease write so a queued arm that keys on the row can never see a claimant vanish mid-release. | `LeaseHold::Drop` removes the hold without setting `lost` (`lease_keeper.rs:159-166`); aborting first would drop the hold (`worker.rs:620` runs on the dropped future) and the detached trainer would write the doomed epoch's bundle into the shared `{job_id}/_resume/` — the regression `trainer.rs:1348-1363` / `crates/jammi-db/src/store/artifact.rs:298-322` exist to prevent. `claim_next` is a client-driven BEGIN/UPDATE/COMMIT (`crates/jammi-db/src/catalog/jobs_repo.rs:713-718` → `crates/jammi-db/src/catalog/backend_postgres.rs:61` begin, `:90` commit): a COMMIT already flushed when tokio drops the loop future is processed by the backend afterwards, and a sweep evaluates the last-committed row version — so the only safe rule is "never abort while a claim can be in flight". |

Invariant: `in_flight > 0 ⇒ the loop is not inside claim_next`. ### 3.2 Startup and warm-before-ready

`OssServer::new` (`runtime.rs:310`) builds the session and, when `preload_models` is non-empty, calls `session.close_worker_gate()` before `bind`. `OssServer::bind` (`runtime.rs:357-376`) is unchanged in shape: health listener bound, gRPC chain assembled and bound (worker spawned inside `assemble_grpc_chain` `:1268` by the unchanged `EmbeddedWorker::spawn(&session)` call, which subscribes to the session's gate, §3.1), `take_worker()` moves the guard into `BoundServer.worker: Option<EmbeddedWorker>`, `metrics.attach_worker(shared)` when `Some`. Then `serve_with_signals(drain_rx, release_rx)`:

1. `BoundServer::serve()` spawns the signal watcher task (one task owns `ctrl_c()` + `terminate()`, polled from process start — tokio coalesces only before the first poll, R8): first SIGTERM → `drain_tx.send(true)`, `phase = Draining`; SIGINT at any time, or any later SIGTERM → `release_tx.send(true)`. The watches are the only coupling between the watcher and `serve_with_signals`.
2. Spawn the health task on its own shutdown receiver (broadcast split); `/healthz` 200, `/readyz` 503 `{"status":"not_ready","detail":"preloading 0/n"}`.
3. Preload inline, per entry: `ModelSource::parse(id)`; task = entry's explicit task, else `catalog.get_model(id)?.task`, else `Err(ServerError::Preload{id, reason: "no models row; give { id, task }"})`; `session.model_cache().preload(&source, task, None)`. Raced with `drain_rx`/`release_rx`: a signal during preload aborts the preload future, then `worker.stop_and_join().await` (the gate is closed and its wait is selected against `stop`, §3.1, so the loop returns without claiming; the task's `upsert_worker` precedes that wait, so the join orders `delete_worker` after it), shuts the health task, `session.close()`, returns `Ok(Drained)`/`Ok(Released)` — never serves. Preload `Err` → `worker.stop_and_join().await`, health shutdown, `session.close()`, `Err(Preload)` → `main` exits FAILURE, listener never served, worker never claimed (gate never opened). On BOTH exits the `workers` row is deleted and awaited BEFORE `session.close()` — never left to `EmbeddedWorker::drop`'s detached `rt.spawn` (`worker.rs:1730-1738`), which `process::exit(0)` and the runtime drop race, and which would run only after `session.close()` in this order; no detached spawn-time upsert exists to race the delete (§3.1). Empty list → warm immediately (existing deployments unchanged).
4. `warm = true`, `session.open_worker_gate()` (the worker's first tick passes `wait_for` and flips its row to `claiming`), `phase = Serving`, `/readyz` 200.
5. Serve gRPC via `BoundChain::serve_with_drain(drain_rx)`.

`PreloadEntry { id: String, task: Option<ModelTask> }` with a hand-written `Deserialize` visiting `str` (bare id) or `map` with exactly `id` and optional `task` (`ModelTask::try_from_db_str`), `expecting("a model id string or { id, task }")` — keeps the layer's typed-error contract under `deny_unknown_fields`. `ServerConfig.preload_models: Vec<PreloadEntry>` (`config/mod.rs:1242`). Liveness 200 throughout, so no `startupProbe` is needed. A `test-hooks` park point `preload_test_hooks::ParkPoint::BeforeLoad` inside `ModelCache::preload` (mirroring `compute_test_hooks`, `jobs.rs:780-781`) is the rendezvous C5's oracles use, because the existing cache pause handle is `#[cfg(test)]` (P7).

### 3.3 DRAIN (first SIGTERM)

1. Signal watcher: `readiness.phase = Draining` (`/readyz` 503 `"draining"`), `worker.begin_drain()` (= `phase = Draining`, `stop.send(true)`, best-effort `set_worker_state('draining')`), `drain_tx.send(true)`. Health side-channel not signalled.
2. `drain_rx` feeds tonic's `serve_with_incoming_shutdown` (`runtime.rs:1062`) — listener closed, GOAWAY on open connections, in-flight requests finish — and the stream ender: `MethodClassLayer` (`limits.rs:595-624`) gains `drain: watch::Receiver<bool>`; on the two streaming paths (`:660`) the body is `PermitBody::Draining { inner, permit, drain: Pin<Box<dyn Future<Output=()> + Send>>, fired }` where `drain = Box::pin(async move { let _ = rx.wait_for(|v| *v).await; })` built once from an owned receiver clone, stored like `sleep` at `:796`; `poll_frame` mirrors the `Deadlined` arm (`:865-908`) but synthesises `UNAVAILABLE` "server draining" via the same trailer path and counts `jammi_grpc_refused_total{reason="draining"}` (`RefusedBound::Draining`, `:164-183`). Deadlined and Draining compose (a stream can carry both). Unaries untouched: an in-flight unary (including inline `run_now`, P13) is bounded only by the runtime's grace then SIGKILL — stated in `deploy-server.md`.
3. `drain_sequence = join(grpc_serve, async { let _ = drain_rx.wait_for(|v| *v).await; worker.stop_and_join().await })` — concurrent; the join half is gated so stop is not sent at t=0. `stop_and_join` (`worker.rs:1684-1703`) now sends `stop = true` on the watch, awaits `state_rx.wait_for(|s| *s != LoopState::Running)` (the in-flight job's own terminal write lands first: keeper alive, heartbeats continue, every epoch bundle lands), then takes and awaits the `JoinHandle` (§3.1), then `delete_worker`. No worker → `NothingToJoin` after the gate.
4. `select! { drain_sequence → Drained{worker_joined}, release_rx.wait_for(|v| *v) → §3.4 }` — release races the whole sequence.
5. Signal the health task; `health_task.await`; `session.close()` (`:566` moves here); `telemetry::flush_otlp()`; `Ok(ShutdownOutcome::Drained)` → `main` returns `ExitCode::SUCCESS` (no blocking work remains).

### 3.4 RELEASE (SIGINT any time, or any signal while draining)

Server arm, in order:

1. `drop(grpc_serve)` — connections severed (PostgreSQL "fast": abort current work, exit promptly). Any inline `run_now` future dies here; its row is left to arm 2 (D11).
2. `worker.release_and_stop()` — the one release mechanism, identical on the library:
   - **2a** `phase = Releasing` (`AtomicU8`, `SeqCst` store; every load `SeqCst`). From this instant `register_job_hold_or_release` self-releases instead of dispatching.
   - **2b** `keeper.release_job_holds(bound = WorkerIntervals.heartbeat)`: sets a `release` flag + `wake.notify_one()` (shape of `shutdown_and_join`, `lease_keeper.rs:456-458`); on the keeper thread, serialised with `renew_all`, snapshot the registered holds and release every `LeaseTarget::Job` this instance holds — ONLY that class: `catalog.release_job_lease(job_id, instance_id, attempts)`; `Ok(true)` → `released = true`, `lost = true` (trainer bails at the next boundary without writing a bundle, `trainer.rs:1093-1097,1356`); `Ok(false)` (inline row, or already gone) → hold untouched; `Err` → log, hold untouched (expiry path). `LeaseTarget::ResultTable { table, writer_id }` holds (`lease_keeper.rs:71`; renewed at `:624-639`) — the SECOND lease class a compute job holds — are never touched here: every `BuildingTable` on the session is adopted under the store's one `writer_id` (D11), so from the keeper's map a loop-claimed materialization's table, an inline `run_now`'s and a library materialization's are indistinguishable, and a per-target release would NULL the wrong lease. The building class is released solely by 2c/2g's linked sweep, and the loop's own `ResultTable` hold flips `lost` through the guarded renewal (2c). Completion via `Notify`, bounded by one heartbeat, never a hang. Before any abort, so every live Job hold's `lost` flips while the hold still exists.
   - **2c** sweep #1, two statements in this order: `catalog.release_jobs_claimed_by(instance_id)` — `UPDATE jobs SET lease_expires_at = NULL, releases = releases + 1, updated_at = $now WHERE claimed_by = $me AND status = 'running' AND execution = 'queued' AND lease_expires_at IS NOT NULL`; then `catalog.release_building_tables_of_claimant(instance_id, writer_id) -> Result<usize>` — a plain UPDATE beside `release_jobs_claimed_by`, a sweep over rows rather than a CAS on one (no `ResultTableCas`), scoped through the jobs linkage: `UPDATE result_tables SET lease_expires_at = NULL WHERE writer_id = $2 AND status = 'building' AND lease_expires_at IS NOT NULL AND table_name IN (SELECT partial_result FROM jobs WHERE claimed_by = $1 AND execution = 'queued' AND status = 'running' AND partial_result IS NOT NULL)` with `$1 = instance_id` and `$2 = session.result_store().writer_id()` (`store/mod.rs:694-695`; the same value every `ResultTable` target this instance registers carries) — an uncorrelated `IN (SELECT ..)`, portable on both backends. The order is safe: the jobs sweep only NULLs `lease_expires_at`, and the subquery's predicate (`claimed_by`, `execution`, `status`, `partial_result`) is untouched by it. The sweep therefore matches exactly the building rows of THIS instance's loop-claimed compute jobs: inline `run_now` rows are excluded by construction (`execution = 'inline'`, `schema.rs:996`), a library materialization outside a job has no jobs row at all (likewise any compute producer that created a second, job-unlinked table under the same writer_id — none exists on the compute path, every `execute_compute` arm threads `Some(job_attempt)`, `jobs.rs:391-478`; such a row would fall to expiry, the existing class), and rows recovery adopted under `"{writer_id}/claim-{uuid}"` (`store/mod.rs:1462`) match neither the writer arm nor the linkage — they expire as today. The loop's own `ResultTable` hold is not flagged and not released here: at the keeper's next pass its renewal carries the `lease_present` arm (D9; SQL list), matches 0 rows on the NULLed lease → `CasFailed` → `lost` (`lease_keeper.rs:643`) within one heartbeat — sufficient, because by 2e the loop task has exited or been aborted and the hold dropped, and an old writer's `finish` (`building.rs:247`) errors instead of promoting. A NULL building lease is immediately claimable by the successor because `claim_expired_building_table` (`result_repo.rs:868-895`) matches through `Owner::ExpiredLease` → `lease_expired_clause` (`:377-381`; `IS NULL OR < now`), so the successor's `dispatch_partial_result` (`jobs.rs:310-333`) takes the claim-and-fail arm → `MaterializeAnew` instead of `BackOff` (`:317-322`; compute producers have no resume, `:274-281`) and no unmatched attempt is burned (a `BackOff` returns without finishing, `worker.rs:1167-1174`, and costs one full lease window plus one attempt). The successor can only re-materialize if `jobs.partial_result` is CLEARED on the `MaterializeAnew` arm: today the column is written exactly once (`create_result_table`'s in-transaction CAS `… AND partial_result IS NULL`, `result_repo.rs:599-603`; the only other writer is the caller-less `record_partial_result`, `jobs_repo.rs:1152-1166`) and never cleared, so every attempt ≥ 2 that reaches `MaterializeAnew` has its own `create_result_table` CAS match 0 rows → `JobAttemptSuperseded` (`:625`) → `record_failed` (`worker.rs:1226-1228`) → terminal `failed` — a PRE-EXISTING defect on today's expiry path (`BackOff` → claim-and-fail → `MaterializeAnew` → superseded), untested (`jobs_compute.rs:351` covers only the `ready`-adopt arm), recorded as an escape at the cut. Fixed in C1 (jobs_repo.rs) because the sweep's value is the recovery: `dispatch_partial_result`'s fail arm (`jobs.rs:331-332`) calls `catalog.clear_partial_result(job_id, instance_id, attempts, table)` = `UPDATE jobs SET partial_result = NULL WHERE job_id = $1 AND claimed_by = $2 AND status = 'running' AND attempts = $3 AND partial_result = $4` (attempt-guarded like every jobs CAS, `:931-934`; idempotent; 0 rows = a peer already cleared or superseded this attempt → the existing `JobAttemptSuperseded` path) BEFORE returning `MaterializeAnew`, so the successor's own `create_result_table` CAS matches. Covers a claim, or a building row, that committed after 2b snapshotted. An `Err` from either statement is logged and the arm continues (§3.5 rows "Catalog unreachable during RELEASE" and "RELEASE, the linked building sweep errors").
   - **2d** `stop.send(true)` on the `watch<bool>`. The loop's pre-claim check reads the watch and its idle sleep is `select!{ sleep(idle_poll), stop_rx.wait_for(|v| *v) }`: level-triggered, no lost wakeup. Once this store is visible the loop cannot enter a new `claim_next`; any `claim_next` still in flight began before it. There is no post-claim stop check (`worker.rs:346-361` runs the claimed job unconditionally) and none is added: a claim that commits after 2d runs into `register_job_hold_or_release`, which self-releases under 2a.
   - **2e** read `in_flight` (`SeqCst`). If `in_flight == 0`: the loop is idle, inside `reclaim_expired_jobs`/`claim_next`, or in the claim→hold prologue (fine-tune `worker.rs:481-541` with awaits at `:494`/`:507`/`:515`; compute `:1099-1179`, `dispatch_partial_result` before the hold at `:1181`) — do NOT abort; wait on `state_rx.wait_for(|s| *s != LoopState::Running)` with bound `WorkerIntervals.heartbeat` (`config/mod.rs:1129-1136`, fed by `[lease] heartbeat_secs`, default 10 s; not a `[worker]` key); on the cooperative exit take the handle and await it (§3.1). On timeout `take()` the handle, `abort()`, drop it — the only path where a claim transaction can be in flight when the abort lands (the bound also spans `reclaim_expired_jobs` at `worker.rs:337`, so a large backlog with healthy PG can trip it: cost only, never corruption). Dropping the loop future inside `claim_next`'s closure (`jobs_repo.rs:713-718`) before COMMIT ALWAYS rolls back on both backends — the sqlx transaction rolls back on drop (`backend_postgres.rs:60-96`, commit `:90`; `backend_sqlite.rs:299-378`, begin on a detached task `:351-356` so the guard always exists, commit `:370`) — while a COMMIT already flushed, or an abort landing between COMMIT and hold registration, lands as outcome (iii) of §3.5. If `in_flight > 0`: the loop is inside a job under a registered hold and not inside `claim_next` (invariant: the loop runs one job inline, `worker.rs:323-363`) — `take()` the handle, `abort()`, drop it immediately (the dropped future runs `LeaseHold::Drop` + `CancelWatcherGuard::drop`, supported path per `:610-621`). `debug_assert!(in_flight <= 1)` here and after the helper's increment: the loop runs one job at a time and `run_now` never increments.
   - **2f** observe `state_rx` terminal (`Stopped | Aborted | Failed`) — the in-task guard reports on every exit path (D4). Bounded: after an abort the task is always parked at an `.await`, so the guard drops at the aborted task's next poll (prompt); otherwise 2f is the tail of 2e's bounded wait, which already saw the terminal value.
   - **2g** sweep #2 UNCONDITIONALLY: the same two statements as 2c, same order (`releases + 1` per matched job row; the linked building sweep catches a building row whose INSERT committed after sweep #1; both idempotent by `lease_expires_at IS NOT NULL`); runs on every path — cooperative exit, immediate abort, timeout abort.
   - **2h** `delete_worker(instance_id)`. The ordering 2g-before-2h is load-bearing: the `workers` row outlives this instance's last lease write, so a queued arm that keys on the row can never observe a claimant that has vanished while its rows still hold live leases.
3. `session.release_job_leases()` only when `BoundServer.worker` is `None`: = 2b then 2c on the session; with no worker it is a no-op by construction — only inline holds and inline rows exist, and every statement skips them (2b's `Ok(false)`, the jobs sweep's `execution = 'queued'`, the building sweep's subquery carrying the same predicate), so no loop-claimed row of either class exists to match — but keeps the surface uniform.
4. Signal the health task; await it; `session.close()` (keeper join is prompt: `shutdown_and_join` wakes via `Notify`).
5. `telemetry::flush_otlp()` (`force_flush` + `shutdown`, P12 — the `OnceLock` never drops).

## 6. Acceptance (RED at base, GREEN on branch)

1. Worker mid-job + SIGTERM → job `completed`, result bytes equal an uninterrupted run, process exits 0 (both backends).
2.
