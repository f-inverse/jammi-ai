## 1. Decisions

Each decision: the principle that decides it, then the code fact.

**D1 — Mechanism, not composition.** Two edge kinds on the existing table: `depends_on` (gating) and `parent_id` (grouping + cascade). No sweep verb, no pipeline DSL, no scheduler process, no new task, thread, interval or knob. *Principle:* discipline test (`MAIN docs/guide/src/philosophy.md:20-27`); actuator rule (`crates/jammi-ai/src/pipeline/recompute.rs:30-34`). *Code fact:* the only control loop in the tree is the worker tick (`crates/jammi-ai/src/fine_tune/worker.rs:324-365`); `Cascade::Downstream` (`recompute.rs:24-28`) is the precedent for "one bounded sweep on one explicit request".

**D2 — `blocked` is a PROJECTION, never stored.** Stored status stays `'queued'`; the claim predicate decides readiness at claim time (claimable = every dependency `completed`); `get_job`/`list_jobs` project `'blocked'` through the identical predicate. *Principle:* actuator rule — a stored `blocked → queued` transition would be a coordinator deciding WHEN. *Code fact:* `idx_jobs_claim(status, execution, claimable, priority DESC, created_at)` (`crates/jammi-db/src/catalog/schema.rs:1017`) is a single-range walk on `status = 'queued'`; a stored `blocked` would need `IN ('queued','blocked')` and break it. Safe because no RETURNING path can surface a stored-queued-with-unsatisfied-dependencies row as claimable: `claim_next` returns `running` (`jobs_repo.rs:705-711`), `claim_by_id` only `inline` rows (`:752-759`, and D7 refuses graph fields on inline), reclaim arm 1a requeues a row whose dependencies were all `completed` at claim time — terminal (`:1399-1406`; `status.rs:70-72`), prune keeps live dependencies alive (D8). Only the two SELECT readers (`:583-588`, `:620-626`) switch to `SELECT_COLS_PROJECTED`; every existing `RETURNING {SELECT_COLS}` (`:154-157`) is unchanged.

**D3 — Readiness is a projection; an OUTCOME is written by ONE mechanism with two call sites: a one-hop push inside the transaction that made it true, and a retire-only fourth reclaim arm for every deeper level.** The transaction is bounded, not the graph: a terminal write (`fail_job` both arms, reclaim arms 1b/2, `cancel_request`'s terminal half) retires exactly the DIRECT `queued` dependants of the single row it just failed or cancelled, in its own transaction (§3.6); a dependant at depth k is retired by Arm 3 (§3.7), which rides every existing reclaim call site and never moves a row toward runnable. *Principle:* actuator rule as narrowed by DIST D5 (`plans/DECISION-DIST-v3.md:19`: "terminal-state propagation that only retires rows, riding existing reclaim call sites, never toward runnable, no new interval or knob"); K2 (a transaction whose row count compounds with graph shape is an unbounded input edge). *Code fact:* fan-out 2 × depth 14 = 32 766 rows in one transaction under a transitive push — inside the worker tick's write transaction (`worker.rs:336-341`) that would block `claim_next`'s outer CAS (`jobs_repo.rs:705-711`) and hold SQLite's single writer (`backend_sqlite.rs:330-334`) for its whole duration; `MAX_DEPENDANTS_PER_JOB` bounds branching only, so the frontier compounds. The one-hop cost is bounded by the live fan-out of ONE job (D-G3). An OUTCOME must be durable because typed `jobs.error` (`:65-66`), `updated_at` for retention (`:1659`), prunability (`:1641-1643`) and waiter termination (`jobs.rs:569-572`; `training_job.rs:57-60`; `grpc/job.rs:213-215`) all key on stored state.

**D4 — Edges in an append-only child table `job_dependencies`, migration 031.** *Principle:* K5 (`MAIN docs/swarm/CONSTITUTION.md:63`; `migrations.rs:8-16`). *Code fact:* arrays are unindexable for the reverse probe the push needs and non-portable across the two backends. pg-boss also uses a `job_dependency` table (§9).

**D5 — `cancelled` is a real terminal status; every honoured cancel lands there; a cancel on an unclaimed row is terminal immediately.** *Principle:* typed status enums (`MAIN philosophy.md:36`); K2. *Code fact:* today an honoured cancel lands `failed` (`worker.rs:661-672`; `jobs.rs:744-748`; `jobs_cancel.rs:490-493` asserts `Failed`), and a cancel on a queued row only sets the flag and waits for a claim to fail it (`jobs_repo.rs:1264-1272`; `worker.rs:1114-1120`). `jobs.status` has no CHECK (`schema.rs:995`) → no migration for the value; `JobStatus::ALL` drives every `IN (...)` (`status.rs:78-102`); `status.rs:240` asserts `from_str("cancelled").is_err()` = the RED oracle. The discrimination lives in ONE place: `Catalog::fail_job(job_id, instance_id, attempts, JobFailure)` routes `JobFailure::Error(JammiError::JobCancelled { job_id })` to the `cancelled` UPDATE only when `job_id == the row being written`; everything else lands `failed` with the Display text (a foreign cancel error is a failure of this attempt, not a cancel of this row). Every `record_failed` site whose error expression is a `JammiError` value passes `JobFailure::Error(&e)` — that is how the two compute-path cancel checkpoints reach the `cancelled` arm: the post-claim `check_cancel` (`worker.rs:1117-1118`; `jobs.rs:496-503` returns `JobCancelled { job_id }` for THIS row) and `execute_compute`'s pre-dispatch `check_cancel` (`jobs.rs:377`), which surfaces as the `Err(e)` arm at `worker.rs:1227-1228`. A non-`JobCancelled` error through `Error(&e)` writes `e.to_string()`, byte-identical to today. `JobFailure::Message` is for `String` payloads only: the `format!(…)` sites and `WorkerJobError::Failed(msg)` (`worker.rs:1866-1871`). *Code fact for "one place":* `run_now` calls `fail_job` directly (`jobs.rs:744-748`), bypassing the private `record_failed` (`worker.rs:2797-2804`), so the worker helper is not a sufficient chokepoint. `terminal_sql_list()` has two readers (`model_repo.rs:520`, `jobs_repo.rs:1660`) — both now include `'cancelled'` (a model is no longer referenced by its producing job once that job is cancelled; desirable). `non_terminal_sql_list()` (`status.rs:91-93`) has one caller (`jobs_repo.rs:1261`) and is REMOVED with `cancel_request`'s rewrite (dead code otherwise).

**D6 — Tenant scope for `depends_on`/`parent_id` is the STRICT predicate** `tenant_id = $t OR (tenant_id IS NULL AND $t IS NULL)`, refused at submit as `JammiError::JobGraphInvalid` → `INVALID_ARGUMENT`. Unknown id and other-tenant id produce the identical message ("dependency `X` is not a job of this tenant" / "parent `X` is not a job of this tenant"). *Principle:* B5, K2; the NOT_FOUND-never-PERMISSION_DENIED rule (`crates/jammi-wire/proto/jammi/v1/job.proto:37-41`). *Code fact:* reads are non-strict (`jobs_repo.rs:586-587`) but cancel (`:1271`) and prune (`:1668-1669`) are strict, so a tenant-X child under a NULL-tenant parent would be unreachable to the cascade — strict at the edge is the only rule under which the cascade and prune can reach every row they must.

**D7 — Both fields refused on `execution = 'inline'`.** *Principle:* K2. *Code fact:* `run_now` is synchronous (`jobs.rs:658-685`); a blocked inline row would block its caller forever, and a cascade's `queued → cancelled` CAS can beat `run_now`'s own `claim_by_id` (`:677-685`), surfacing as "failed to claim its own freshly-submitted inline job" (`:681-684`) with no defined semantics. Enforced inside `submit_job_graph` (the `MAX_IDEMPOTENCY_KEY_BYTES` defence-in-depth pattern, `:458-471`) and at the gRPC edge (`grpc/job.rs:141-153` pattern).

**D8 — Prune rule: a terminal row is prunable only if every dependant and every child is terminal; edges cascade on delete.** *Principle:* K2 fail-closed; `prune_jobs` never deletes a non-terminal row (`:1641-1643`). *Code fact:* the guarantee has three legs and the FK is load-bearing: (i) the prune predicate reads committed edges; (ii) a dependant of a `failed`/`cancelled` row can only exist if it was submitted before that row went terminal (submit refuses otherwise), so its edge is committed before prune could consider the row; (iii) the in-flight window — an edge being inserted while prune evaluates — is closed on Postgres by the FK check's `KEY SHARE` lock on the dependency row, which blocks `DELETE` (§9), and on SQLite by the single writer (`backend_sqlite.rs:330-334`). `REFERENCES jobs(job_id) ON DELETE CASCADE` on BOTH edge columns must never be simplified away; migration 031's rustdoc says so.

**D9 — Dedupe per row.** A keyed resubmit that collides returns the winner's id and ignores the resubmit's `depends_on`/`parent_id`, exactly as it ignores the spec (`INSERT … ON CONFLICT DO NOTHING RETURNING`, `:479-490`, `:524-556`). Edges are inserted only on the fresh-insert branch, same transaction.

**D10 — Wire: fields only, no new RPC; freeze baseline unchanged.** *Code fact:* `api_freeze.rs:46-65` tokenises `PACKAGE` and `RPC` only; `api_freeze_baseline.txt` has no field lines. Refutes the brief's "freeze baseline updated"; `wire_surface_equals_the_frozen_baseline` (`:78-97`) runs as the proof.

**D11 — Reason typing.** `JammiError::JobDependencyFailed { job_id, dependency_id, dependency_status }` (Display → `jobs.error`, the one vocabulary; minted in Rust, never in SQL) and `JammiError::JobGraphInvalid { job_id, message }`, both in `crates/jammi-db/src/error.rs` beside `JobCancelled` (`:255-264`); wire encode/decode arms + exhaustive lists (`crates/jammi-wire/src/error.rs:162-164`, `:266`, `:885-890`, `:953-955`); `error.proto` messages (tags 30/31 after `not_recomputable = 29`, `error.proto:92`; 15 stays reserved, `:103-104`); `map_engine_error` (`grpc/wire.rs:109`): `JobGraphInvalid → InvalidArgument`, `JobDependencyFailed → FailedPrecondition`. `JobCancelled` already round-trips typed (`wire/error.rs:162-164`, `:266`; `grpc/wire.rs:223-225` → `Code::Cancelled`).

**D12 — Both arms carry the typed `JobCancelled`; the Python client has no gRPC-code arm for it.** Embedded `JobHandle::wait` (`jobs.rs:547-576`), `TrainingJob::wait` (`training_job.rs:48-64`) and the Python binding's `wait_for_result` (`crates/jammi-python/src/job.rs:359-386`) return `Err(JammiError::JobCancelled { job_id })` on `cancelled`; `to_pyerr`'s class table (`crates/jammi-python/src/error.rs:52-77`, today `_ => "BackendError"`) gains `JobCancelled → "JobCancelled"` and `JobGraphInvalid → "InvalidArgument"` (`client_error` resolves the class by name at raise time, `:23-28` — lockstep, K6). Remote `RemoteJob.wait` (`clients/python/jammi/_database.py:834-848`) raises `class JobCancelled(JammiError, RuntimeError)` (the `errors.py:10-13` convention: a training failure IS a `RuntimeError`, so `except RuntimeError` keeps working for callers who caught the former `TrainingError`) on `resp.status == "cancelled"` — and ONLY there. `_rpc_to_jammi` (`_database.py:99-129`) gains no `CANCELLED` arm: grpc `CANCELLED` is also produced client-locally, the pure-Python client decodes only `code()`/`details()` (`:120-121`), and no unary of `JobService` surfaces `JobCancelled` (`grpc/job.rs:273-304` return status strings and booleans); a typed-detail decoding seam for the Python client is out of scope (§7). `_TERMINAL_STATES` (`_database.py:590`) gains `"cancelled"`. The Rust client's `wait_job` stream (`crates/jammi-client/src/lib.rs:435-440`) is unchanged (frames); consumers reconstruct from `done.status == "cancelled"`. *Principle:* K4; `Err(FineTune(text))` would be the wrong domain for a generic handle.

**D13 — One `SubmitJobParams`, one `submit_job_graph`.** `#[derive(Default)]` compiles on `&str` fields (`Default for &str = ""`); only `JobExecution` (`status.rs:193-199`) lacks `Default` — one line (`#[default] Queued`). `SubmitJobParams<'a>` (`jobs_repo.rs:267-287`) gains `pub depends_on: &'a [&'a str]`, `pub parent_id: Option<&'a str>` and `#[derive(Default)]`. `Catalog::submit_job_graph(p, idempotency_key) -> Result<SubmittedJob { job_id, fresh, initially_blocked }>` is the one insert; `submit_job_deduped(p, key) -> Result<String>` stays as a thin alias returning `job_id`; `submit_job` unchanged (`:411-414`). The 41 literal sites (§4 C2) gain `..Default::default()` — compiler-caught (B6).

**D-G3 — Bounds.** `MAX_DEPENDENCY_DEPTH = 64` bounds the submit-time `UNION` walk only (§3.4 step 2) — nothing else loops over it. `MAX_DEPENDS_ON = 1024` (K2 at the edge; ≤ 500 chunking keeps every statement under both backends' bind limits). `MAX_DEPENDANTS_PER_JOB = 4096` is a SOFT bound on the NON-TERMINAL dependants of one job, checked at submit (§3.4 step 1b): `FOR SHARE` does not conflict with `FOR SHARE` (proven live), so concurrent submits can overshoot by one edge each; no test asserts it hard. Counting non-terminal dependants only is what bounds the one-hop push (it retires `queued` rows, a subset of non-terminal) and keeps a long-lived hub dependable after its old dependants retire. `ARM3_BATCH = 500` is a constant beside `MAX_ATTEMPTS` (`worker.rs:123`), not a knob.

**Forks.** **F1** Cycles impossible by construction: ids are minted immediately before submit (`jobs.rs:607`, `:659`; `session.rs:1655`; `context_predictor.rs:545`), no caller-chosen id exists anywhere, validation runs inside the insert transaction against committed rows (`FOR SHARE` on PG / `BEGIN IMMEDIATE` on SQLite), self-dependency is refused in Rust and by `CHECK (job_id <> depends_on_job_id)`, and a child cannot be submitted before its parent (the parent must exist). Concurrent A(deps B)/B(deps A) both fail validation. **F2** A blocked job holds no lease: queued rows have `lease_expires_at NULL`; arms 1a/1b/2 predicate on `running` (`:1403`, `:1441`, `:1479`); Arm 3 predicates on `queued` and only ever writes a terminal status. **F3** Cascade onto a running child = `cancel_requested = TRUE`, never kill; honoured at the executor's checkpoints (`jobs.rs:36-57`; `worker.rs:549-578`, `:2564-2611`), landing `cancelled` via D5. **F4** `parent_id` has NO FK: CASCADE would delete children younger than retention, SET NULL erases grouping, RESTRICT breaks prune; existence + tenant are enforced at the edge (D6); `idx_jobs_parent` serves the list filter and the cascade walk.

## 3. Design

### 3.1 Migration 031 (`"031_job_graph"`, appended after `migrations.rs:104`; takes the next free number at rebase)

```sql
ALTER TABLE jobs ADD COLUMN parent_id TEXT;
ALTER TABLE jobs ADD COLUMN has_deps BOOLEAN NOT NULL DEFAULT FALSE;
CREATE INDEX idx_jobs_parent ON jobs(parent_id);
CREATE TABLE job_dependencies (
    job_id            TEXT NOT NULL REFERENCES jobs(job_id) ON DELETE CASCADE,
    depends_on_job_id TEXT NOT NULL REFERENCES jobs(job_id) ON DELETE CASCADE,
    PRIMARY KEY (job_id, depends_on_job_id),
    CHECK (job_id <> depends_on_job_id)
);
CREATE INDEX idx_job_dependencies_reverse ON job_dependencies(depends_on_job_id);
```

One `ADD COLUMN` per statement (P3). No FK on `parent_id` (F4). No `idx_jobs_gated`: a partial index on the gated rows does not change Arm 3's cost class (§3.7 — the semi-join is evaluated for every gated queued row whichever index drives the scan), so it would be a second index for nothing. `has_deps` is written ONLY by the INSERT in `submit_job_graph` (`= !depends_on.is_empty()`) and is immutable thereafter (edges are append-only). Rustdoc on the constant states the D8 three-leg argument and that both FK `ON DELETE CASCADE` clauses are load-bearing. `SELECT_COLS`/`parse_row`/`JobRecord` gain `has_deps: bool`, `parent_id: Option<String>`.

### 3.2 Status vocabulary

`JobStatus` gains `Blocked` (non-terminal, projected only, never stored) and `Cancelled` (terminal); `ALL` = six in lifecycle order; `is_terminal = Completed | Failed | Cancelled`; Display/FromStr arms `"blocked"`, `"cancelled"`. New helper `terminal_unsuccessful_sql_list()` = `'failed', 'cancelled'` (terminal and not `Completed`), rendered from `ALL` like `terminal_sql_list()` (`status.rs:84-86`). `non_terminal_sql_list()` is removed (D5). `JobRecord::is_terminal` parses through `JobStatus` instead of two string compares. `JobExecution` gains `#[derive(Default)]` / `#[default] Queued`. Reconcile (`store/reconcile.rs:689`) filters `Queued || Blocked` so a blocked job keeps its `_resume/**` prefix.

### 3.3 The one readiness predicate, rendered twice

Rust helper in `jobs_repo.rs`:

```
fn unsatisfied_dependency_sublink(alias: &str) -> String  // 'completed' rendered from JobStatus::Completed
  = "(SELECT 1 FROM job_dependencies d LEFT JOIN jobs p ON p.job_id = d.depends_on_job_id \
       WHERE d.job_id = {alias}.job_id AND (p.job_id IS NULL OR p.status <> 'completed') LIMIT 1)"
```

`LEFT JOIN … IS NULL` is fail-closed against a vanished dependency (K2; covers any FK-off window).

**Claim** (`claim_next` candidate, replaces `:688-699`; `claimable = TRUE` on both arms):

Postgres:
```sql
(SELECT j.job_id FROM jobs j
  WHERE j.status = $3 AND j.execution = ${execution_bind} AND j.claimable = TRUE
    AND j.kind IN ({kind_in})
    AND CASE WHEN j.has_deps THEN {unsatisfied_dependency_sublink("j")} IS NULL ELSE TRUE END
  ORDER BY j.priority DESC, j.created_at LIMIT 1 FOR UPDATE OF j SKIP LOCKED)
```
SQLite: identical text without `FOR UPDATE OF j SKIP LOCKED`. The outer `UPDATE … WHERE job_id = {candidate} AND status = $3 RETURNING {SELECT_COLS}` (`:705-711`) is unchanged.

**Projection** (`SELECT_COLS_PROJECTED`, used only by `get_job` and `list_jobs`): `SELECT_COLS` with `status` replaced by
```sql
CASE WHEN jobs.status = 'queued' AND jobs.has_deps
     THEN CASE WHEN {unsatisfied_dependency_sublink("jobs")} IS NULL THEN jobs.status ELSE 'blocked' END
     ELSE jobs.status END AS status
```
(nested `CASE`, not `AND`, because Postgres does not define `AND`/`OR` operand order — §9). `parse_row` untouched.

**Why this shape (measured).** The scalar sublink `(SELECT … LIMIT 1) IS NULL` is an EXPR sublink: Postgres cannot apply `convert_EXISTS_to_ANY` to it, so it never becomes the hashed O(catalog) SubPlan a `NOT EXISTS` form produced; it runs per `has_deps` row with two PK probes and stops at the first unsatisfied edge. `UNION ALL` two-branch forms are illegal with `FOR UPDATE` on PG 16.15 (`ERROR: FOR UPDATE is not allowed with UNION/INTERSECT/EXCEPT`). The bare `AND claimable` at `:691`/`:696` is a pre-existing SQLite defect — not an index-usable equality, so every poll today materialises and sorts the whole `(queued, queued)` range; `claimable = TRUE` makes it a three-column index constraint whose remaining columns satisfy the `ORDER BY`. `TRUE` is a keyword on SQLite ≥ 3.23 and the column is `BOOLEAN` stored 1/0 by sqlx; migration 029's `DEFAULT TRUE` (`schema.rs:1012`) already relies on it; Postgres already planned the bare form as `claimable = true`.

| Shape | PG 16.15 | SQLite 3.46.0 |
|---|---|---|
| base, bare `AND claimable`, 10k blocked-ahead | 5 buffers / 0.019 ms (returns a *blocked* row) | plan `SEARCH … (status=? AND execution=?)` + `USE TEMP B-TREE FOR ORDER BY`; 4.0 ms at 20k rows |
| base, `claimable = TRUE`, 20k zero-edge | 4 buffers / 0.019 ms, `Index Cond` includes `claimable = true` | plan `SEARCH … (status=? AND execution=? AND claimable=?)`, no TEMP B-TREE; 16 µs |
| CASE form, `claimable = TRUE`, 20k zero-edge | 4 buffers / 0.019 ms; `SubPlan 1 … (never executed)` | `CORRELATED SCALAR SUBQUERY` under the same SEARCH; 27 µs; `IfNot` on `has_deps` jumps over the subroutine |
| CASE form, 10k blocked-ahead (10k edges to `running` deps) | per-row `SubPlan 1` `loops=10000`, `Index Only Scan job_dependencies_pkey` + `Index Scan jobs_pkey`; 60 129 buffers / 21.8 ms = 6 buffers per blocked row | 12 ms |

Honest bound: zero-edge cost is within noise of the fixed base on both backends; blocked-ahead cost is O(blocked-ahead × edges) with index probes (~2 µs per blocked row on PG, ~1.2 µs on SQLite). Any correct claim must examine every higher-priority blocked row; no shape avoids it without a stored readiness transition (D2).

### 3.4 Submit — `Catalog::submit_job_graph(p: SubmitJobParams, idempotency_key: Option<&str>) -> Result<SubmittedJob>`

Constants beside `MAX_IDEMPOTENCY_KEY_BYTES` (`:400`): `pub const MAX_DEPENDENCY_DEPTH: usize = 64;`, `pub const MAX_DEPENDS_ON: usize = 1024;`, `pub const MAX_DEPENDANTS_PER_JOB: usize = 4096;` (rustdoc: soft, D-G3).

Rust-side normalisation before the transaction (each refusal is `JobGraphInvalid { job_id, message }`): drop empty strings, dedupe, sort `depends_on`; refuse `depends_on.len() > MAX_DEPENDS_ON`; refuse self in `depends_on` or as `parent_id`; refuse `execution == Inline` with either field set (D7); refuse an empty-string `parent_id` (treated as `None` at the wire edge instead).

Inside the existing write transaction (`:475-572`), before the INSERT, only when either field is set:

1. **Validation SELECT**, strict tenant, ids = `depends_on ∪ {parent_id}`:
   - Postgres: `SELECT job_id, status FROM jobs WHERE job_id IN ($1..$n) AND (tenant_id = $t OR (tenant_id IS NULL AND $t IS NULL)) FOR SHARE`
   - SQLite: same text without `FOR SHARE` (the transaction is already `BEGIN IMMEDIATE`, P5).
   - Any id absent from the result → `"dependency `X` is not a job of this tenant"` / `"parent `X` …"` (identical for unknown and cross-tenant, D6). A dependency whose status is `failed`/`cancelled` → `"dependency `X` is already {status}"`. A parent may have any status.
   - `initially_blocked = any(dep.status != completed)` — zero extra statements.
   1b. **Fan-out count** (only when `depends_on` is non-empty): `SELECT d.depends_on_job_id AS dep, COUNT(*) AS live FROM job_dependencies d JOIN jobs j ON j.job_id = d.job_id WHERE d.depends_on_job_id IN ($deps) AND j.status NOT IN ({terminal_sql_list}) GROUP BY d.depends_on_job_id` (driven by `idx_job_dependencies_reverse`); any `live >= MAX_DEPENDANTS_PER_JOB` → `"dependency `X` already has {live} live dependants (MAX_DEPENDANTS_PER_JOB = 4096)"`.
2. **Depth check** (K2): `WITH RECURSIVE anc(job_id, depth) AS (SELECT job_id, 1 FROM jobs WHERE job_id IN ($deps) UNION SELECT d.depends_on_job_id, a.depth + 1 FROM anc a JOIN job_dependencies d ON d.job_id = a.job_id WHERE a.depth < 64) SELECT MAX(depth) FROM anc` — `UNION` (not `UNION ALL`) dedups `(node, depth)`, bounding a diamond at N×64; refuse if `MAX(depth) >= MAX_DEPENDENCY_DEPTH` (the new node would sit at depth 65). The same walk upward over `parent_id` seeded from `parent_id` at depth 1 bounds the cancel tree with the same constant.
3. **INSERT** (`:479-490`) gains `parent_id, has_deps` in its column list.
4. **Fresh-insert branch** (`:524-526`): `INSERT INTO job_dependencies (job_id, depends_on_job_id) VALUES ($1,$2), …` in sorted order, chunked ≤ 500 rows per statement; return `SubmittedJob { job_id, fresh: true, initially_blocked }`.
5. **Collision branch** (`:536-556`): skip edges; return `{ job_id: winner, fresh: false, initially_blocked: false }` (the caller re-reads, P22).

**Race argument (why the one-hop push can never miss an edge).** On Postgres the validation `FOR SHARE` holds every dependency's row: an `UPDATE … SET status` on a row held `FOR SHARE` by another session blocks (measured: `canceling statement due to lock timeout … while updating tuple`), whereas the FK's own `KEY SHARE` does not block it — hence the explicit `FOR SHARE`, not the FK, is what serialises submit against the failing write. Either the failing write commits first and the SELECT sees `failed` and refuses, or the submit commits first and the failing write, which waited on the share lock, runs its push under a statement snapshot that includes the new edge. On SQLite the two writers are serialised by `BEGIN IMMEDIATE`. No deadlock cycle: the submit acquires `FOR SHARE` then only inserts (its FK `KEY SHARE` is compatible with its own share lock). Two concurrent submits naming the same dependency do not serialise against each other (`FOR SHARE` is compatible with `FOR SHARE`), which is why 1b is soft. Cost: 7 buffers / 0.015 ms for two dependencies. Interaction with the claim: while a submit's validation transaction holds `FOR SHARE` on a dependency row, `claim_next`'s `SKIP LOCKED` skips that row (a brief priority inversion for the window of one submit) and a finish/fail/cancel on it blocks for the window — operability.md carries this sentence.

`initially_blocked` is exact at commit on both backends and thereafter monotone and self-healing: a `blocked` handle can only ever read `queued`/`running`/terminal later, never the reverse, and the first `status()` read returns the projection.

### 3.5 The one retire statement — `retire_queued_rows(tx, to: Retirement, rows: &[(String, String)]) -> Result<Vec<String>>`

Every write that moves a `queued` row to `failed` (dependency failure) or `cancelled` (cascade on an unclaimed row) is this ONE statement, issued once per chunk of ≤ 500 `(job_id, msg)` pairs, `msg` minted in Rust from the single `JammiError` Display vocabulary before the statement is rendered:

```sql
WITH v(id, msg) AS (VALUES ($1, $2), ($3, $4), …, (${2k-1}, ${2k}))
UPDATE jobs
   SET status = '{to.status}', error = v.msg, {extra}
       acceleration_report = CASE WHEN acceleration_report = ${2k+1} THEN ${2k+2} ELSE acceleration_report END,
       updated_at = ${2k+3}
  FROM v
 WHERE jobs.job_id = v.id AND jobs.status = '{queued}'
RETURNING jobs.job_id
```

`k` = the ACTUAL chunk length; `retire_pending_report_clause(2k+1, 2k+2)` (`jobs_repo.rs:218-223`) composes unchanged with indices computed from `k`; the `now` bind is `2k+3`. A constant index would silently bind NULL on SQLite for every chunk shorter than 500: sqlx-sqlite 0.8.6 `arguments.rs:106-114` `break`s out of binding when a placeholder's index exceeds `values.len()` ("SQLite treats unbound variables as NULL; we reproduce this here"), so the retire clause would compare against NULL and `updated_at` would be written NULL — a `NOT NULL` violation on a partial final chunk on SQLite, and a type error on Postgres. A15 pins this with a partial final chunk on both backends. `Retirement::DependencyFailed` renders `to.status = 'failed'` (from `JobStatus::Failed`), terminal marker `ACCELERATION_REPORT_DEPENDENCY_FAILED = {"state":"undetermined","reason":"dependency_failed"}`, `{extra}` empty; `Retirement::Cancelled` renders `'cancelled'`, marker `ACCELERATION_REPORT_CANCELLED = {"state":"undetermined","reason":"cancelled"}`, `{extra} = cancel_requested = TRUE,`. `'{queued}'` is rendered from `JobStatus::Queued` like `:484`. The CTE spelling is the portable one (SQLite 3.46.0 rejects `FROM (VALUES …) AS v(id, msg)`); `UPDATE … FROM` needs SQLite ≥ 3.33 (bundled 3.46.0). RETURNING = the winners: per-row CAS semantics are preserved by `jobs.status = 'queued'`, so a row a concurrent claim or cancel moved first is simply not returned. `RETURNING` order is unspecified on both backends and tracks neither the `v` input order nor any upstream `ORDER BY` (measured: a descending `v` input came back ascending on PG 16.15 and on SQLite 3.46.0, while another fixture came back in input order on PG), so `retire_queued_rows` SORTS its winners ascending by `job_id` in Rust before returning them — part of its contract, consumed by the push's log line (§3.6), Arm 3's returned winners (§3.7) and the cascade's push order (§3.9 step 2). Rows are passed in ascending `job_id`; `lease_expires_at` is already NULL on a queued row. The rows counter (§3.11) records `k` per statement.

### 3.6 One hop, inside the writer's transaction — `push_dependency_failure_one_hop(tx, dependency_id, dependency_status) -> Result<usize>`

Called by every terminal-non-success write (§3.8, §3.9) with the ONE row it just wrote, inside the same transaction:

1. `SELECT d.job_id FROM job_dependencies d JOIN jobs j ON j.job_id = d.job_id WHERE d.depends_on_job_id = $1 AND j.status = '{queued}' ORDER BY d.job_id` — driven by `idx_job_dependencies_reverse`.
2. Per returned row mint `JobDependencyFailed { job_id, dependency_id, dependency_status }.to_string()`; `retire_queued_rows(tx, DependencyFailed, rows)` in ≤ 500-row chunks; the winners come back ascending per chunk (§3.5) and are logged in that order; their count is the return value.

Duplicate-free BY CONSTRUCTION: `depends_on_job_id` is fixed and `PRIMARY KEY (job_id, depends_on_job_id)` admits one edge per dependant, so no dependant appears twice in `v` and the named dependency is exactly the job that failed. The count is for logging; it is never appended to reclaim's `out` (P19: `reclaim_job_on_read` pops the last element of that vec). The push runs INSIDE the writer's transaction — for reclaim arms 1b/2 that is the tick's write transaction, which blocks `claim_next`'s outer CAS UPDATE (`:705-711`) and holds SQLite's single writer for the chunks' duration; the cost is bounded by the live fan-out of ONE job (≤ `MAX_DEPENDANTS_PER_JOB` plus concurrent-submit overshoot). Atomicity: a crash mid-push rolls back the terminal write too; reclaim re-fails it later with a fresh push. Measured: from one just-failed row, PG 9 buffers / 0.020 ms with one dependant, 2 buffers / 0.008 ms with none; SQLite 51 µs; the set form at 10 000 dependants is 22 ms PG / 62 ms SQLite (per-row CAS would be 465 ms PG, round-trip bound — why the set form); the 4 096-dependant hop is A10's documented measurement.

### 3.7 Arm 3 — retire dependants of a terminal-unsuccessful dependency (fourth reclaim arm, retire-only)

`fn retire_dependants_of_failed_dependencies(tx, scope: Option<&str>, limit: usize) -> Result<Vec<String>>`, `pub const ARM3_BATCH: usize = 500;`. Two statements when there is work, one when there is none:

1. Candidate SELECT (`{tu}` = `terminal_unsuccessful_sql_list()` = `'failed', 'cancelled'`; `{queued}` from `JobStatus`):
```sql
SELECT j.job_id,
       (SELECT MIN(p.job_id) FROM job_dependencies d JOIN jobs p ON p.job_id = d.depends_on_job_id
         WHERE d.job_id = j.job_id AND p.status IN ({tu})) AS dep_id,
       (SELECT q.status FROM jobs q WHERE q.job_id =
          (SELECT MIN(p.job_id) FROM job_dependencies d JOIN jobs p ON p.job_id = d.depends_on_job_id
            WHERE d.job_id = j.job_id AND p.status IN ({tu}))) AS dep_status
  FROM jobs j
 WHERE j.status = '{queued}' AND j.has_deps
   AND EXISTS (SELECT 1 FROM job_dependencies d JOIN jobs p ON p.job_id = d.depends_on_job_id
                WHERE d.job_id = j.job_id AND p.status IN ({tu}))
   {AND j.job_id = $1}   -- the statement's only bind; present only for the scoped form
 LIMIT {limit}
```
   The named dependency is `MIN(p.job_id)` among that row's failed/cancelled dependencies — an aggregate, not `ORDER BY … LIMIT 1`, because SQLite 3.46.0 plans a correlated `ORDER BY … LIMIT 1` sublink with `USE TEMP B-TREE FOR ORDER BY` while `MIN` plans without one (measured, docs/plans/68-compute-tier-substrate/pressure/measurements/pt6/g_sq.sql); deterministic on both backends; its status rides in the second sublink (a PK lookup on that MIN) so the text is minted in Rust from the single Display. The SELECT-first shape is chosen over `UPDATE … WHERE job_id IN (SELECT … LIMIT $n)` because the latter would have to render the error text in SQL (a second vocabulary) or follow the UPDATE with a further UPDATE; SELECT-then-`retire_queued_rows` keeps ONE retire statement for every writer. `LIMIT` on the SELECT is portable (Postgres has no `UPDATE … LIMIT`).

   **Cost model (measured on PG 16.15).** The `EXISTS` is never a hashed SubPlan; its join strategy and driving side are statistics-dependent (a Nested Loop Semi Join off `idx_jobs_claim` when the edge table is large, a Hash Semi Join fed from `idx_job_dependencies_reverse` when it is small — both legitimate; the gate asserts the cost class, not the strategy, A10(g)): with `ORDER BY j.job_id` the planner walks `jobs_pkey` and filters — 113 000 rows scanned, 29 425 buffers / 15.0 ms per pass at 50 000 retained failed rows with NOTHING to retire — which is why the SELECT carries no `ORDER BY` (the no-`ORDER BY` form is planned as a bitmap scan on the `status = 'queued'` prefix of `idx_jobs_claim`, filtered on `has_deps`). The winners are sorted ascending by `job_id` in Rust before `retire_queued_rows` (its input contract, §3.5); the named-dependency determinism is per row, from the `MIN` aggregate, so it is unaffected. Even so the floor of a pass is O(gated queued rows): the semi-join is evaluated for every `queued AND has_deps` row (~6 buffers per row on PG — the same per-row cost the claim predicate pays for every blocked-ahead row, §3.3), `LIMIT` cannot short-circuit when nothing qualifies, and a partial index on the gated rows does not change that class (§3.1). Measured on the permanent `jobs` table (113 000 rows incl. 50 000 retained terminal dependants and their edges, `VACUUM (ANALYZE)`d): 24 166 buffers / 9.5 ms per pass at 4 000 gated queued rows with nothing to retire (the floor); 34 082 buffers / 12.8 ms when a full `ARM3_BATCH` of 500 retires (the ceiling — the two sublinks execute once per winner). `{limit}` is rendered as an INTERPOLATED LITERAL (house style: every `LIMIT` in the tree is interpolated — `store/mutable/postgres.rs:154`, `sqlite.rs:150`, `audit/query.rs:59`, `source/mutable.rs:717`; the tree contains no `LIMIT $n` anywhere), never a bind: sqlx 0.8 prepares every statement persistently per connection (`catalog/backend.rs:288-320`) and PG switches to the generic plan from the sixth execution, which with a bound limit was measured to change the driving side to `Seq Scan on jobs` (25 958 buffers / 13.5-14.6 ms) — the shipped plan must be the measured plan. With the limit a literal the BULK statement (`scope = None`) carries no bind at all, so PG never has a custom plan to choose (the generic path is taken outright when there are no bound parameters) and that generic plan is built with every literal in place: it IS the plan A10(g) EXPLAINs, at every execution count. Everything interpolated into this statement is Rust-derived and constant — `{tu}` (`terminal_unsuccessful_sql_list()`), `{queued}` (`JobStatus`), the presence of the scope clause, and `{limit}` (a `usize` formatted with `{}`: `ARM3_BATCH` = 500 at call site (a), `1` at call site (b)) — so there is no injection surface; the one caller-supplied value, `scope`, stays a BIND (`$1`, the scoped form's only placeholder). The scoped form therefore does keep a parameter and may go generic from its sixth execution — it is excluded from A10(g) and measured separately at 11-33 buffers through `jobs_pkey`. A pass pays the floor whether or not it retires anything, and one runs at every call site below — every tick of every worker, and boot; it is the cost class the claim predicate already accepts, bounded by the gated backlog. The TEMP-table figures are confirmed by a live-lane re-measure on the permanent `jobs` table (A10(g)) before the operability sentence (§3.12) lands.
2. Sort the rows ascending by `job_id`; per row mint `JobDependencyFailed { job_id, dependency_id: dep_id, dependency_status: dep_status }`; `retire_queued_rows(tx, DependencyFailed, rows)`; return the winners (ascending, §3.5).

**Call sites (existing, no new interval).** (a) The bulk sweep: `reclaim_expired_jobs_inner(lease, max_attempts, None)` (`:1347`) calls it after Arm 2 (before `:1490`) with `scope = None, limit = ARM3_BATCH`; `inner` returns `ReclaimOutcome { rows: Vec<JobRecord>, retired: Vec<String> }`; `reclaim_expired_jobs` (`:1316-1321`) returns `rows.len() + retired.len()`. Between the failure and its retirement a dependant is projected `blocked` and is never claimable (§3.3: the claim predicate requires every dependency `completed`, and a terminal-unsuccessful dependency can never become `completed`). ### 3.9 Cancel — `cancel_request(job_id) -> Result<bool>` (`:1256-1287`)

One transaction, four steps. Tree = `WITH RECURSIVE tree(job_id, depth) AS (SELECT job_id, 0 FROM jobs WHERE job_id = $root UNION ALL SELECT c.job_id, t.depth + 1 FROM jobs c JOIN tree t ON c.parent_id = t.job_id WHERE t.depth < 64)` (syntax confirmed on PG 16.15 and SQLite 3.46.0). `UNION ALL` is safe because the parent graph is a forest: a parent must exist at submit, ids are fresh uuids, and `parent_id` is never rewritten, so no node is reachable twice and the depth bound is the only cut needed.

1. `SELECT job_id FROM jobs WHERE job_id IN (SELECT job_id FROM tree) AND status = 'queued' AND {strict tenant | admin} ORDER BY job_id` → per row mint `JobCancelled { job_id: that row }.to_string()` → `retire_queued_rows(tx, Cancelled, rows)` → `cancelled_ids` (winners).
2. For each id in `cancelled_ids`, in the ascending order `retire_queued_rows` returns them (§3.5): `push_dependency_failure_one_hop(tx, id, "cancelled")`. A dependant of two cancelled siblings is retired by the first push (it then no longer matches `status = 'queued'`, so the second push's SELECT does not return it) — no dedupe rule, and its named dependency is the lowest cancelled sibling id because the winner list is sorted, not because `RETURNING` has an order.
3. `UPDATE jobs SET cancel_requested = TRUE, updated_at = $now WHERE job_id IN (SELECT job_id FROM tree) AND status = 'running' AND cancel_requested = FALSE AND {strict tenant | admin}`.
4. Return `cancelled_ids.len() + rows3 > 0`.

Race with a concurrent claim: both CAS on `status`; exactly one wins; if the claim wins, step 3 flags the now-running row and the executor lands `cancelled` at its checkpoint via §3.8, whose own push then reaches its dependants. A terminal root still cascades to non-terminal descendants. Two concurrent cascades over overlapping trees, or a cascade concurrent with a push that locks rows in a different order, can deadlock on PG (`40P01`), surfaced as a backend error to that caller; the retry is idempotent. `CancelJobResponse.cancelled` doc: "at least one row in the parent tree was affected".

### 3.13 Failure modes

| Situation | Behaviour |
|---|---|
| Nonexistent / other-tenant / self / failed-or-cancelled dependency at submit | Refused `JobGraphInvalid` → `INVALID_ARGUMENT`; no row, no edge |
| Depth would exceed 64; > `MAX_DEPENDS_ON`; ≥ `MAX_DEPENDANTS_PER_JOB` live dependants on a named dependency; inline with either field | Refused `JobGraphInvalid` |
| Dependency fails after submit (`fail_job`, arm 1b/2) | Direct dependants: `failed` with `JobDependencyFailed{…,"failed"}` in the same transaction; deeper levels: projected `blocked`, never claimable, retired by Arm 3 within the §3.7 pass bound |
| Dependency cancelled (unclaimed cascade or honoured) | Same, `dependency_status = "cancelled"` |
| Worker dies mid-run of a dependency | Arm 1a requeues it; dependants stay `blocked`; nothing pushed |
| Submit races the dependency's failing write | Serialised by `FOR SHARE` / `BEGIN IMMEDIATE` (§3.4): refused or pushed, never stored-queued with a failed dependency (A14) |
| Two submits race on the same dependency near 4 096 | Both may pass 1b; the bound is soft by one edge per concurrent submit (D-G3) |
| Crash mid-push / mid-Arm-3 pass | Whole transaction rolls back; the next pass or the next terminal write repeats it (idempotent) |
| Dependency pruned while dependant live | Impossible (D8); raw-SQL deletion → FK cascade removes the edge, dependant becomes claimable (operator's action); `LEFT JOIN … IS NULL` fails closed in any FK-off window |
| Cancel parent with running children | Flagged; they land `cancelled` at their checkpoints (compute: pre-dispatch only, `jobs.rs:377`; training: watcher/epoch boundary) and push one hop to their dependants |
| Cancel a terminal parent | Cascade still reaches non-terminal descendants; returns `true` iff any row affected |
| Overlapping cascades, or a cascade against a push (PG) | One aborts `40P01` → backend error to that caller; retry idempotent |
| Blocked job with no worker | Stays `blocked` like `queued` (`operability.md:220`); a direct dependency failure is still pushed by whoever writes it; deeper levels wait for a pass (boot sweep, any tick, or a read of that row) |
| Keyed resubmit collides | Winner's id; resubmit's graph fields ignored (D9); handle re-reads projected status |
| `JobHandle::wait` embedded on a `blocked` row | Polls `get_job` (`jobs.rs:549`) — sees `failed` as soon as the push or a pass commits; the embedded `wait` does not call reclaim-on-read (pre-existing asymmetry, out of scope) |
| `WaitJob` on a depth-k dependant | Each iteration's `get_job` projects the row `blocked`; `reclaim_job_on_read` then runs the scoped Arm 3 and retires the row as soon as its direct dependency is terminal-unsuccessful; the stream ends with `Done{status:"failed", error}` |
